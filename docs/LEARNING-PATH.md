# 全栈学习路线与项目讲解

这条路线围绕一个能运行、能复算、能解释的保险业务闭环推进。先阅读 [PROJECT-DESIGN.md](./PROJECT-DESIGN.md) 的业务规则，再用 [API-CONTRACT.md](./API-CONTRACT.md) 对照前后端输入输出。

不要先背完整技术清单。每一步都把“页面上的动作→HTTP 请求→服务端规则→数据库变化→页面反馈”串起来，并保存一个能复现的例子。

## 第一步：跑通工程并画出一条请求

学习内容：

- Java 17、Maven 的编译与依赖关系，Spring Boot 的入口及配置文件。
- Vue 3 工程入口、Vite 开发服务器、TypeScript 和组件结构。
- 前端 `/api` 代理与后端接口地址的关系；浏览器 Network 中的请求、响应和状态码。
- H2 demo 与 MySQL 运行方式的区别，配置如何选择数据源。

实践产出：

1. 按项目启动说明启动前后端，用演示账号登录。
2. 在 Network 中找到验证码、登录和当前用户请求，记录成功与失败返回。
3. 画出“登录表单→接口→认证服务→用户资料→页面导航”的调用链。

也可打开后端 `/swagger-ui/index.html` 查看自动生成的请求模型。验证码和登录接口无需认证，业务请求需要在 Authorize 中填写登录返回的随机令牌。将文档里的字段与 `Requests.java` 对照，理解参数校验和接口描述分别负责什么。

达到的理解：能够说明“页面能打开”和“后端可用”是两件需要分别检查的事；能判断一个错误发生在代理、接口、权限还是数据库连接阶段。

面试可讲：前后端分离的请求路径、统一响应结构、开发代理用途、如何定位一次登录失败。

## 第二步：从一个查询页学习 Vue 与接口契约

先研究参保人员列表，再研究编辑表单。

- 掌握组件、响应式状态、计算属性、生命周期与事件。
- 理解 TypeScript 接口类型如何约束列表行、表单和 API 返回值。
- 将请求函数与页面组件区分职责，处理加载、空数据、错误和提交中状态。
- 认识搜索、状态筛选和界面分页。当前契约列表返回数组，不把它说成已经实现服务端分页。
- 阅读路由与权限菜单，区分“看不见按钮”和“服务端拒绝越权”。

实践：给一条虚构参保人员做新增、修改、停用，并观察每次网络请求和数据库记录。不要只展示修改后页面，要检查刷新页面后数据仍然存在。

面试可讲：组件如何划分、表单如何防止重复点击、前端类型与后端校验为什么都需要。

## 第三步：从一个写接口学习 Spring Boot 与数据库

沿着参保维护请求阅读 Controller、业务服务和 Mapper。

- Controller 处理参数与响应，服务负责业务规则，Mapper 负责持久化。
- 使用参数校验表达必填、长度、范围等约束；业务关联是否允许修改由服务处理。
- 理解 MyBatis-Plus 的映射、查询和更新；查看实际 SQL，而不只调用通用 CRUD。
- 阅读主键、唯一约束、外键关系或等效业务校验、索引和时间字段。
- 理解停用与物理删除对历史关联的影响。

实践：尝试重复卡号或其他受唯一规则保护的数据，观察系统如何返回错误；确认被历史业务引用的资料无法被直接物理删除。

面试可讲：一个写接口各层的职责、数据库约束如何补充代码校验、为什么保险和手术资料需要保留历史关联。

## 第四步：独立复算计费，再读实现

先手算，再对照 `/visits/quote` 和就诊提交接口：

```text
手术 300.00 × 2，诊断费 100.00，报销率 70%
总费用 700.00，拟报销 490.00，自付 210.00
```

要理解：

- 为什么金额使用十进制类型，不能直接用二进制浮点计算金融金额。
- 为什么先舍入报销额，再由总额减去报销额求自付。
- 为什么手术价格和费率从服务端取，不信任前端传来的计算结果。
- 为什么报价不扣款，提交仍需要重新校验、重新计算。
- 为什么单据保存费率、价格和名称快照，而非显示时重新查询当前价格。

实践：提交一张单后修改保险费率和手术价格，查看旧单明细不变，再预览一张新单，验证它使用新规则。

面试可讲：金额精度、服务端作为计费依据、历史快照解决的业务问题。例子中的 70% 是项目演示值，不把它讲成实际医保政策。

## 第五步：完成一次拒赔与部分补缴

沿用设计文档中的案例：卡余额 300.00 元，就诊先扣 210.00 元，剩 90.00 元；拒赔补扣 90.00 元，形成 400.00 元待补缴。充值 200.00 元后主动补缴，剩 200.00 元欠款；再次充值并补缴后结清。

要理解：

- 审核状态与支付状态分别表达什么。
- 为什么审核通过不再次扣卡；模拟医院结算应如何统计。
- 为什么拒赔成功也可能仍有欠款。
- 为什么充值与补缴要分开，部分补缴怎样计算。
- 为什么存在待补缴时要阻止新增就诊。
- 怎样用流水核对余额，怎样用单据核对待补缴。

实践产出：用表格记录每一步的请求、余额、拟报销额、待补缴、审核状态、支付状态和资金流水。每行金额都能解释来源。

面试可讲：一个完整的状态机、异常分支如何闭环、如何区分资金余额与待收费用。

## 第六步：学习身份、权限与数据范围

分别以医生、审核员、管理员登录，验证同一个 URL 和接口在不同角色下的行为。

- Spring Security 如何处理身份认证、令牌和权限检查。
- 密码怎样存储和校验，验证码为什么一次性使用。
- 角色关联权限代码，菜单与按钮如何使用权限。
- 医生只能看本人登记的就诊，为什么查询详情时也要检查归属。
- 文件列表与下载为何都要校验上传者或管理员身份。
- 操作日志与业务审核记录分别回答什么问题。

实践：用医生账号直接请求其他医生的单据详情，确认后端拒绝或不返回该记录；直接请求无权限的审核接口，确认服务端拒绝。不要以“菜单隐藏了”作为权限验证完成。

面试可讲：认证与授权的区别、功能权限与数据范围的区别、后端如何防止通过修改 ID 越权。

## 第七步：用重复请求理解事务和幂等

先阅读一次就诊提交涉及哪些数据库写入，再验证它们同时成功或同时回滚。

- `@Transactional` 的作用与边界；异常发生后哪些数据需要一起回滚。
- 唯一约束如何处理两个并发请求都判断“尚未处理”的竞争。
- 数据库锁或原子更新如何保护余额、待补缴和审核状态。
- `requestId` 为何在同一操作重试中保持不变。
- 同一请求标识携带不同参数为什么应该拒绝。
- 按钮禁用为何无法覆盖网络重试、双标签页和两个审核员并发。

实践清单：

1. 同一个充值请求发送两次，仅增加一次余额。
2. 同一个就诊请求重复提交，仅有一张单和一次自付扣款。
3. 两个审核请求并发处理同一单，只有一个决定生效。
4. 多个扣款同时使用同一卡，不能出现负余额或丢失流水。
5. 主动制造服务端处理失败，确认未留下半笔扣款。

面试可讲：用实际复现过的重复提交或并发案例解释问题、修复和证据。若仅在 H2 测过，应准确说 H2 下的结果；在 MySQL 复测事务和锁之后，再说 MySQL 环境也通过验证。

## 第八步：完善全栈交互与数据展示

- 让医生填写就诊时能看懂费用组成，让审核员能追溯费率与金额。
- 表单提交成功后使用服务端返回值更新界面；提交失败时给出能继续处理的原因。
- 区分“没有数据”“正在加载”“请求失败”“没有权限”。
- 首页图表从业务记录计算；已结算金额只统计通过审核的单据。
- 确认日期、金额、状态文案一致，拒赔部分补缴展示剩余欠款。
- 文件下载正确携带身份信息，名称和错误提示清楚。

首页采用 Vue-ECharts 管理图表更新、尺寸适配和销毁，`src/charts/` 定义模块注册与有类型的选项。学习时可以先定位柱图、折线图、饼图分别依赖哪些 ECharts 模块，再看 Vite 分包配置为什么不能强制导入完整入口。运行 `npm test` 检查真实 SVG 渲染回归，运行 `npm run build` 查看生产分包大小。SVG 渲染测试覆盖模块和数据语义；浏览器中的 Canvas、容器尺寸和交互仍需在页面检查。

开源项目的选择依据、许可和本次体积比较见 [OPEN-SOURCE-REUSE.md](./OPEN-SOURCE-REUSE.md)。讲解时区分采用组件依赖、参考管理模板与自己实现的业务规则。

实践：选择一个异常场景录制短演示，例如“余额不足→管理员充值→医生提交成功”，说明前后端怎样共同完成这次操作。

面试可讲：前端如何反映后端业务状态、如何处理网络失败后的重试、图表指标如何防止误算。

## 第九步：构建验证证据并复现部署

优先把测试投入到公式、权限、状态迁移和资金变化，避免给每个简单访问器写没有业务价值的测试。

| 验证层次 | 适合的场景 | 应保存的证据 |
| --- | --- | --- |
| 业务单元测试 | 舍入边界、费用合计、部分补缴公式 | 固定输入、期望结果和通过记录 |
| 接口或集成测试 | 登录权限、就诊提交、审核、事务回滚 | 请求、响应和数据库断言 |
| 并发验证 | 重复请求、竞争审核、同账户并发支出 | 操作次数、最终状态、余额及流水核对 |
| 页面验收 | 三角色路径、加载和错误状态、金额展示 | 演示步骤和对应截图 |
| MySQL 与打包验证 | 数据源切换、构建、启动、刷新后持久化 | 实际环境、命令、版本和结果 |

使用仓库当前提供的启动脚本和构建说明，实际完成一次前端构建与后端打包。能解释开发服务器与构建产物的区别，确认刷新页面、直接访问路由、前后端地址配置等行为。

只有实际配置并验证了 Nginx，才将 Nginx 部署写进项目经历。只有代码真实使用并验证 Redis 的用途，才把 Redis 缓存或会话存储作为已实现能力。Docker Compose 中存在一个容器本身不能证明这些能力。

## 第十步：整理全栈简历与面试讲法

先做一份“功能—代码入口—验证证据”清单，再写简历。例如：

| 候选亮点 | 写入简历前需有的证据 |
| --- | --- |
| Vue 3 + Spring Boot 前后端分离 | 可运行页面、真实接口与数据库读写 |
| 三角色权限与医生数据范围 | 越权接口和跨医生单据访问均有验证 |
| 计费快照与报销审核闭环 | 可复算算例、旧单不变、通过及拒赔流程 |
| 幂等与事务保护 | 重复请求只记账一次，失败完整回滚的验证 |
| 拒赔余额不足与部分补缴 | 金额守恒、状态变化、最终结清的完整演示 |
| 部署与运维 | 实际完成过的环境和可重复启动步骤 |

只选择已经实现并验证的内容。待做项留在路线中，不能写成成果；没有压测依据，就不写并发量、响应时间提升或性能百分比；没有真实用户，就不写覆盖医院数量或业务规模。

完成对应功能后，可以按实际情况组织项目描述：

> 基于 Vue 3、TypeScript、Spring Boot 和 MyBatis-Plus 开发大病保险教学管理系统，贯通参保维护、就诊计费、报销审核与医保卡资金流水。通过费用快照保留历史规则，并完成拒赔余额不足、部分补缴及结清流程。

如果幂等、并发和权限验证也已经完成，可进一步加入具体机制和验证案例。依赖清单里有某个库，并不等于具备可讲述的实现经验。

一次五分钟项目讲解可以按下面的顺序进行：

1. 解释三种角色和一个完整业务案例。
2. 展示费用预览、就诊提交、审核和补缴。
3. 从页面进入接口，再进入服务与数据库，讲清一条主链路。
4. 选一个解决过的问题，例如重复扣款或历史费率变化，展示处理办法与验证证据。
5. 说明当前完成范围及下一项有明确价值的改进。

## 学习记录建议

每完成一个阶段，记录四件事：我改了什么、它解决什么业务问题、请求和数据库怎样变化、用什么证据确认有效。遇到问题时保留能重现的最小步骤，修复后使用同样步骤复测。

项目最终的学习成果应是能够独立解释并修改一条业务链路，而不仅是运行一份代码或记住技术名称。
